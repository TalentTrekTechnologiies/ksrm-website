# KSRM College CMS — Schema Edge Case Review (Phase 1 + Phase 1B)

Companion to `DATA_MODEL_DESIGN.md`. 122 schema-level edge cases identified in a structured review of the additive schema (`prisma/schema.prisma`) and its two generated migrations, covering relationships, constraints, nullability, cascading behavior, uniqueness, concurrency, migrations, and future extensibility, as requested.

Items 1–101 are from the original Phase 1 review. **Items 102–122 (categories N and O) were added in Phase 1B**, covering the RBAC granularity redesign and the 10 new page-driven content entities. Item 85 was also revised in place (marked below) since the change it described no longer applies after the RBAC redesign.

**Scope note:** this is a *schema*-level review. It deliberately does not re-cover application-layer bugs already documented in the earlier stabilization-phase audit (`PROJECT_HANDOFF.md`) — the two documents are complementary.

Each item states the condition, why it's safe or what needs to happen to keep it safe, and where relevant, a cross-reference to the design doc section governing it.

---

## A. Foreign key / referential integrity (20)

1. `Faculty.departmentId` is nullable in Phase 1 — a Faculty row can exist with no department at all until backfilled. Every query written against the new schema must handle `null` here until Phase 3's backfill completes.
2. `Faculty.departmentRef` uses `onDelete: SetNull`. Deleting a `Department` while nullable-linked Faculty exist silently orphans them (their `departmentId` becomes `null`) rather than blocking the delete. This is intentional for the transitional/nullable period; §9 Phase 4 tightens this to `Restrict` once the column is `NOT NULL`.
3. `Department.hodId → Faculty.id` uses `SetNull`. If the HOD's Faculty row is deleted, the department is left with no HOD (`hodId` nulled) rather than blocking the deletion, and there's no automatic reassignment.
4. `Department.hodId` is `@unique`, enforcing "a Faculty member can be HOD of at most one department" — but it's also nullable, so it does *not* enforce "every department has an HOD." A vacant HOD position (`hodId = null`) is valid.
5. `Faculty.departmentId` (their employer) and `Department.hodId` (who is HOD) are independent relations. Nothing in the schema enforces that a department's recorded HOD actually works in that same department — assigning department X's `hodId` to a Faculty member whose `departmentId` is department Y is not structurally prevented and must be enforced at the application layer.
6. `Lab.inChargeFacultyId` uses `SetNull` — deleting a faculty member removes them as lab in-charge but leaves the `Lab` row otherwise intact; no cascading delete of the lab itself.
7. `CommitteeMember.facultyId` is optional, supporting external (non-faculty) members. This means `name`/`designation` can legitimately diverge from the linked `Faculty` row's current values — by design (see §D.42/§F.58's snapshot reasoning), not a bug to "fix" by syncing them.
8. `News.categoryId` and `News.authorAdminId` are both independently nullable in Phase 1 — a News row can have a category but no author, an author but no category, or neither, during the transitional period.
9. `News` has two separate relations to `Admin` (`authorAdminId`, `deletedBy`), requiring explicit `@relation` names to disambiguate. A future third `Admin` relation added without a name would be a Prisma schema error (self-enforcing), not a silent bug — but the pattern must be followed consistently as new relations are added.
10. `AuditLog` now has *both* the original unconstrained `adminId: Int` and the new `adminRefId: Int?` FK. Application code (Phase 6) must decide which is authoritative going forward; until then, two different admin-identifying columns coexist on the same row.
11. `Category` is shared across 4 content domains via `domain: CategoryDomain`, but nothing stops assigning a `NEWS`-domain category's ID to `GalleryImage.categoryId` — the FK only checks that a `Category` row with that ID exists, not that its `domain` matches the content type. Enforce this at the application/DTO layer.
12. `Download` has two overlapping classification systems on the same row: a `category: DownloadCategory` enum *and* a `categoryId → Category` FK. These could disagree (e.g. `category: SYLLABUS` while `categoryRef` is tagged `domain: DOWNLOAD, name: "Brochures"`). Flagged as a design smell to resolve before Phase 6, not resolved here.
13. `Committee`'s unique constraint is `(type, name)`, not `(type)` alone — deliberately, so multiple `OTHER`-type committees can coexist. The side effect: nothing stops creating a near-duplicate, e.g. a second `ANTI_RAGGING` committee with a slightly different name.
14. `RefreshToken.adminId` uses `Cascade` — deleting an `Admin` row deletes all their refresh tokens. The application never actually hard-deletes admins today (only deactivates via `isActive`), so this path is currently unreachable/untested in practice.
15. `AdminRole`/`RolePermission` cascade on either side. Deleting a `Permission` silently strips it from every role that had it, with no confirmation step at the DB level — a genuinely destructive action a future admin UI should guard with its own confirmation.
16. `SiteSetting.updatedBy` uses `SetNull` — "who last changed this" attribution is lost if that admin is later removed, same as every other `deletedBy`/`authorAdminId` field.
17. `Faculty` is the FK target from five different places (`Department.hodId`, `Lab.inChargeFacultyId`, `CommitteeMember.facultyId`, plus its own `departmentId`/`deletedBy` pointing outward). A "can I delete this faculty member" check needs to account for all five relationships, not just their department assignment.
18. `Department` is referenced from ten different tables. An eventual "delete this department" action is one of the highest-blast-radius operations in the schema; once Phase 4 tightens the relevant relations to `Restrict`, it will correctly fail loudly rather than orphan data — but the admin UX should show the full dependency count before allowing the attempt.
19. Department-optionality is intentionally asymmetric: Faculty/Placement/DegreeVerification/Research are conceptually "must have a department" (becoming `NOT NULL` + `Restrict` at cutover) while GalleryImage/ExamNotification/Download/Admin are conceptually "may or may not" (staying nullable + `SetNull` permanently). Easy to implement inconsistently if not tracked per-table, as §3 of the design doc does.
20. `Faculty.email` has no `@unique` constraint (deliberately deferred — see §7 item 7). Two Faculty rows can share an email today, inconsistent with `Admin.email`'s existing global uniqueness. Must be resolved (duplicate check + cleanup) before the constraint is safely added.

## B. Nullability (10)

21. Every new FK column added in Phase 1 is nullable specifically so existing rows don't need a value yet. Any application code written against the new schema *today* must handle `null` on all of them, or it will crash against any pre-existing/unbackfilled row.
22. `Faculty.experience` stays `String?` (e.g. `"15+ years"`) rather than a structured `Int`. Sorting/filtering "10+ years experience" needs string parsing in application code, not a numeric `WHERE` clause — an accepted tradeoff for real-world data variety.
23. `DegreeVerification.cgpaOrPercentage` is optional and doesn't record *which scale* (CGPA out of 10, or percentage out of 100) a given value is on. `"7.8"` is ambiguous without an accompanying convention — needs a documented rule (or a follow-up `scale` field) before this column is relied upon.
24. `Lab.capacity` being optional doesn't distinguish "genuinely unknown" from "not applicable" (e.g. a seminar-hall-style lab). No sentinel exists for that distinction.
25. `CommitteeMember.role`/`designation` are required (not nullable) — every member must have both filled in before the row can be saved at all; no "draft" partial-save state exists.
26. `SiteSetting.description` is optional — settings can exist with zero explanation of what they control. Nothing enforces documentation quality.
27. Every `deletedBy` field stays nullable even after `deletedAt` is set (e.g. a system/scripted deletion with no acting admin) — any "who deleted this" UI must handle a null admin reference gracefully (e.g. show "System"/"Unknown"), not crash.
28. `RefreshToken.revokedAt` being `null` means "still valid" — but that alone doesn't mean *usable*; the application must also check `expiresAt > now()` together with it. Neither field alone tells you whether a token currently works.
29. A `Download` can have no category at all, *or* a `categoryId` pointing at a `Category` whose `domain` isn't `DOWNLOAD` (see A.11). These are two distinct failure modes needing distinct validation messages.
30. `News.date` (the original, required column) was deliberately **not** renamed to `publishedAt` in Phase 1, unlike the earlier full-scope proposal — renaming an existing column is out of scope for an additive migration. Whether to rename it later, or just keep `date` permanently, is an open decision, not resolved here.

## C. Uniqueness / composite constraints (8)

31. `News.slug` is `@unique` but nullable. Postgres treats `NULL` as distinct from itself for uniqueness purposes, so every existing row can safely have `slug: null` simultaneously; the constraint only engages once two *different* rows share the same *non-null* value.
32. Once slugs are backfilled and required, soft-delete interacts badly with this constraint: a soft-deleted `News` row still permanently occupies its slug under a plain unique index. Republishing under the same slug after "deleting" the original requires either accepting slugs can never be reused, or a Postgres partial unique index (`WHERE deletedAt IS NULL`) — not representable directly in Prisma's schema DSL, and not implemented in Phase 1.
33. The same slug/soft-delete tension applies to every other unique-plus-soft-deletable field: `LearningOutcome`'s `(departmentId, type, code)`, `Committee`'s `(type, name)`. A soft-deleted row still blocks recreating an identical key.
34. `RefreshToken.tokenHash @unique` relies on cryptographic hash uniqueness (SHA-256-class collision resistance), not just "we hope these don't collide" — worth stating explicitly why this constraint is safe to trust.
35. `Role.name`/`Permission.key` are globally unique with no soft-delete concern, but if a `Role` is ever renamed, its old name immediately becomes available for reuse by an unrelated new role — a reason any future audit trail should log roles by ID, not name.
36. `Category`'s `@@unique([domain, slug])` permits the same slug string across *different* domains (`"events"` can exist once for `NEWS` and once for `GALLERY`). A category lookup must always filter by domain, never by slug alone.
37. `DegreeVerification.hallTicketNo @unique` (pre-existing, unchanged) is global, not scoped by department or year — worth confirming this matches KSRM's actual hall-ticket numbering scheme before this constraint is relied on in a public verification flow.
38. `Faculty` has no unique constraint on `(departmentId, name)` — two faculty in the same department can share a name (a real, if rare, possibility). "Look up faculty by name within a department" can never safely assume uniqueness.

## D. Cascade / onDelete behavior (7)

39. **Soft-delete completely bypasses every `onDelete` rule in this schema.** `Restrict`/`SetNull`/`Cascade` only fire on a real SQL `DELETE`; a soft-delete is an `UPDATE`, which the FK engine doesn't distinguish from any other update. Soft-deleting a `Department` does *not* automatically cascade to, or get blocked by, its Faculty/Labs at the database level. This is the single most important caveat for whoever implements Phase 6.
40. Direct consequence of #39: it's entirely possible to end up with a soft-deleted `Department` that still has fully "live," non-deleted Faculty/Labs pointing at it. Application code must decide and enforce a policy (block, or cascade the soft-delete) — the schema permits either outcome.
41. `Lab → Department` uses `Cascade` (a real hard-delete cascade) while `Lab → Faculty` (`inChargeFacultyId`) uses `SetNull` — two different cascade philosophies on the same table, intentional (Department genuinely owns its Labs; a Lab doesn't stop existing just because its in-charge left) but must be understood together, not assumed identical.
42. `Committee → CommitteeMember` uses `Cascade` — deleting a Committee wipes its entire membership roster instantly, bypassing `CommitteeMember`'s own soft-delete columns entirely (Cascade operates at the SQL `DELETE` level regardless of the child table's own soft-delete support).
43. Every `deletedBy` FK uses `SetNull`, never `Restrict`/`Cascade` — deliberately, so it always remains possible to remove an Admin account without that action being blocked by, or destroying, everything they'd ever soft-deleted. The tradeoff: "who deleted this" attribution eventually erodes for departed admins.
44. `AdminRole`/`RolePermission` cascade in both directions — bulk-deleting Permissions during a catalog cleanup silently and immediately strips them from every role that had them, with no soft-delete/undo step (`Permission` isn't soft-deletable).
45. `Faculty → Department` uses `SetNull` in Phase 1's nullable transitional state but is documented to become `Restrict` once `NOT NULL` at cutover (§9 Phase 4) — the *cascade behavior itself* changes over the migration's lifetime, not just nullability. Tests written against Phase-1 behavior will need revisiting post-cutover.

## E. Enums (5)

46. Postgres enums require a schema migration to add a new value — unlike a lookup table, a genuinely new `CommitteeType` can't be added purely through the admin panel. A deliberate tradeoff for "fixed, code-meaningful vocabulary," made per §1 principle 3, but it cuts against admin-panel-only extensibility.
47. Conversely, `OTHER` (in `CommitteeType`/`DownloadCategory`) is an escape hatch that defeats the enum's purpose if overused. If most real rows end up tagged `OTHER`, that's a signal the fixed values were chosen too narrowly — not a signal to keep routing more data through `OTHER` indefinitely.
48. Reordering or removing enum values in a *future* migration is a nontrivial Postgres operation (adding a value is supported via `ALTER TYPE ... ADD VALUE`; removing/reordering generally requires recreating the type) — a real constraint on how freely these enums can evolve later, distinct from #46's "adding" case.
49. `SiteSettingType` describes the *intended* type of `SiteSetting.value`, but `value` is stored as plain `String` — nothing in the database enforces that a `type: NUMBER` row actually contains a parseable number. Validation is entirely an application-layer responsibility; a manual `UPDATE` could silently desynchronize a setting's declared type from its actual content.
50. `ProgrammeLevel` (`UG`/`PG`/`PHD`/`DIPLOMA`) has no distinct value for something like "PG Diploma" (common in many Indian institutions' programme catalogs, distinct from both `PG` and `DIPLOMA`). Designed from general domain knowledge, not confirmed against KSRM's actual programme list — worth checking before relying on it.

## F. Soft delete mechanism (8)

51. Because Phase 1 adds `deletedAt`/`deletedBy`/`version` as pure schema additions with no application code changes, every *existing* query in every *existing* service will keep returning "soft-deleted" rows once the concept is actually used, until every one of those queries is updated to filter `WHERE deletedAt IS NULL`. Until Phase 6, the columns exist but enforce nothing.
52. There is no database-level mechanism (view, Postgres Row-Level Security) in this design that automatically excludes soft-deleted rows from ordinary queries. Prisma doesn't natively support a global "always exclude deleted" filter without either a Client Extension applied everywhere, or remembering the filter by hand in every query — a real, easy-to-get-wrong operational risk for Phase 6.
53. Soft-deleting a row does *not* release any of its unique constraints (see C.32/C.33) — the single biggest practical soft-delete gotcha here, needing an explicit product decision before Phase 6.
54. A soft-delete-only update will typically also bump `updatedAt` (since Prisma's `@updatedAt` fires on any `update`, including one that only sets `deletedAt`) — "last updated" and "last content edit" become indistinguishable once soft-delete is in play, unless the application deliberately special-cases a delete-only update.
55. Restoring a soft-deleted row (`deletedAt` back to `null`) is entirely possible with this data model but not yet implemented anywhere — no trash/restore UI, endpoint, or permission exists yet. This document only guarantees the *data* needed to build one.
56. Entities deliberately left out of the soft-delete scope (`Research`, `ExamNotification`, `DegreeVerification`, `Notification`) remain genuinely, permanently hard-deleted even after Phase 6 ships soft-delete elsewhere. A generic "restore from trash" UI must not imply that capability exists for these.
57. `Admin` deliberately has no `deletedAt`/`deletedBy` pair — `isActive` already serves an equivalent purpose for that one entity. This makes the soft-delete *semantics* inconsistent by design across the schema: content entities can have `isActive` (business toggle) *and* `deletedAt` (trash) independently; `Admin` only has one mechanism doing both jobs. Any future entity extending this pattern must decide up front which it needs.
58. `CommitteeMember.isActive` and `CommitteeMember.deletedAt` coexist, giving three genuinely different states: (a) active & not deleted (currently serving), (b) inactive but not deleted (on leave/term ended, kept for historical roster display), (c) deleted (removed entirely, e.g. added by mistake). A naive query might collapse this into two states if not careful.

## G. Optimistic locking / concurrency (6)

59. `version` only *detects* a conflict; it doesn't resolve one. If an update's `WHERE id = ? AND version = ?` ever gets written without including `version` in the `where` and incrementing it, the column becomes purely decorative with zero actual protection.
60. Prisma's `P2025` ("record not found") fires both when the ID truly doesn't exist *and* when the ID exists but the version doesn't match. The application must distinguish 404 from 409 by checking existence separately (or re-fetching after a P2025) — the schema alone can't disambiguate.
61. Nothing stops a buggy or compromised client from sending an artificially lower "expected version" than the row's current value — the database will correctly reject it as "no match" (safe failure), but confirm the application never lets a client dictate the expected version beyond what it was actually handed on the last read.
62. Optimistic locking protects conflicting *writes*, not conflicting *reads* — two admins can both load the same record at `version: 3`; only the first to save succeeds. There's no "someone else has this open" warning mechanism here (that would need something entirely outside this schema's scope, e.g. real-time presence).
63. `version` is scoped to exactly the same 12 entities as soft-delete. Entities outside that list (`Research`, `ExamNotification`, `DegreeVerification`, `Notification`, `Admin`, `Category`, `SiteSetting`, `Permission`, `Role`) have zero conflict detection — two admins concurrently editing the same `ExamNotification` will have the second save silently overwrite the first. Confirm this is acceptable for those specific entities before Phase 6.
64. A soft-delete should almost certainly also increment `version`, so another admin who had the row open gets a conflict on their next save rather than accidentally "reviving" a just-deleted row by overwriting `deletedAt` back to null via an unrelated field update. Flagged now so Phase 6's implementation doesn't overlook it.

## H. Migration / rollback safety (8)

65. Every new Phase 1 column is nullable or carries a `@default(...)` — exactly what makes `ADD COLUMN` instant and lock-free on Postgres regardless of table size. Verified none of the 10 `ALTER TABLE` statements in the generated migration require a full table rewrite.
66. This migration was generated via an *offline* schema-to-schema diff, not `prisma migrate dev` against a live database — it has not been execution-tested against a real running Postgres with real data, consistent with this environment's lack of live database access throughout this engagement.
67. Rolling back Phase 1 is a straightforward reverse (`DROP TABLE` × 15, `DROP COLUMN` for every additive column, `DROP TYPE` × 6 enums, drop the new indexes/FKs) — nothing existing was touched or backfilled, so a rollback purely discards brand-new, still-empty structure.
68. `RolePermission`/`AdminRole` use composite primary keys, not a surrogate `id` — a deliberate, permanent choice for pure join tables. This means neither table can later gain a simple integer `id` without a breaking schema change (dropping and recreating the primary key). Confirm no future feature (e.g. per-grant audit history) would need to reference a specific join row by its own identity.
69. All 6 new enums are created fresh; `CREATE TYPE` isn't idempotent. Prisma's own migration-tracking table prevents a *whole* migration from silently re-running, but a manually, partially-applied migration (SQL run by hand outside Prisma) wouldn't be protected by that safety net.
70. The 55 new indexes all build on either brand-new (empty) tables or nullable columns with no populated values yet — none will be slow today. Once Phase 3's backfill populates real data into these columns, any *further* schema change to them should consider `CREATE INDEX CONCURRENTLY`, which this migration didn't need to.
71. This migration's SQL was verified (direct grep, not just asserted) to contain zero `DROP TABLE`/`DROP COLUMN`/`RENAME`/`ALTER COLUMN ... TYPE` statements. That check only covers *this* migration — future migrations layered on top need the same explicit verification repeated, not assumed from precedent.
72. `prisma/migrations/migration_lock.toml` (recording the DB provider) was left completely untouched — confirmed by direct comparison before/after — preserving Prisma's built-in safety net against applying a migration history to the wrong database engine.

## I. Future extensibility (8)

73. Every new FK column uses a plain `Int` matching the referenced table's auto-increment PK. If multi-tenancy (§8) is ever pursued, every referenced table gains an `institutionId`, and each existing FK needs reconsidering: a plain ID reference likely remains *valid* even in a multi-tenant world (IDs stay globally unique), but the application layer would additionally need to verify the referenced row's `institutionId` matches — not automatic, and not decided here.
74. The RBAC design has no concept of a permission scoped to one *specific* department instance (e.g. "manage faculty, but only in CSE"). Today, `Admin.departmentId` plus the `Department Administrator`/`Department Editor` roles rely entirely on application code checking "does this admin's department match the resource's department" alongside the permission check — no row-level/attribute-based access control exists in the schema itself.
75. `SiteSetting` is a flat `key`/`value`/`group` model with no nesting — deeply structured configuration (e.g. a multi-field "social links" block) becomes either several flat keys (`social.twitter`, `social.linkedin`) or one `type: JSON` value holding a stringified nested object. A convention should be picked deliberately before Phase 6 builds the settings admin UI, not decided ad hoc per setting.
76. `Research.departmentId` was added and the entity got a proper place in the ERD, but the `Research` NestJS module (controller/service) still doesn't exist — a pre-existing gap noted in the original stabilization audit. The schema is now more ready for a Research module than the application code is.
77. `Committee`/`CommitteeMember` are scoped only to real committees (Anti-Ragging, Grievance Redressal) per your instruction. `CommitteeType.OTHER` can technically accommodate a future Women's Cell or SC/ST Cell committee without a migration (just a new row tagged `OTHER`), but won't get a dedicated, type-safe enum value (and filtering like "all Women's Cell committees") until one is actually built and the enum is deliberately extended.
78. `DownloadCategory` and `CategoryDomain.DOWNLOAD` overlap conceptually (both classify a `Download` — see A.12). Resolving this (likely picking one classification system) is recommended future work before Phase 6, not decided here.
79. No new table has full-text search indexing (Postgres `tsvector`/GIN), even though `News.content`, `Department.about`, and faculty bios are exactly the long-form text a real CMS eventually wants searchable. Deliberately out of scope for a purely additive Phase 1 migration.
80. No table has a `locale`/language column. A future bilingual (e.g. English/Telugu) requirement would need either a `locale` discriminator + composite-uniqueness changes on every content table, or a separate translations side-table per entity — a substantial, non-trivially-additive future change, flagged so it's a conscious decision if it comes up.

## J. RBAC seed data specifics (5)

81. All 9 seeded roles are marked `isSystemRole: true` — meaning, per that field's stated purpose, none are meant to be deletable by whatever "protect system roles" logic gets built later. If one turns out to be a poor fit, the correct fix is editing its permission set or seeding a new custom role alongside it, not deleting/renaming a seeded one.
82. The seed's role→permission mapping encodes an opinionated hierarchy (`Department Administrator` is a strict superset of `Department Editor`'s permissions) that the *schema* does not itself enforce or preserve — if `Department Editor` is later edited in an admin UI to also grant `faculty.manage`, the two roles become functionally identical with no schema-level concept of "role hierarchy" to notice the drift.
83. The seeded `Super Admin` role having every permission in the catalog is cosmetic/documentational only — `PermissionsGuard`'s actual bypass checks `Admin.isSuperAdmin: Boolean` directly and does not consult this role's permission list at all. Granting the "Super Admin" role to someone is *not* equivalent to setting `isSuperAdmin: true`; the two mechanisms are entirely disconnected today.
84. Seeding via `upsert` (keyed on `key`/`name`) makes re-running `prisma/seed.ts` safe and idempotent for *additions*, but it does not remove `RolePermission` links that were deleted from a role's list in the seed script (or via a future admin UI) on a prior run — stale permission grants aren't cleaned up by re-seeding.
85. **[Revised in Phase 1B]** The `Viewer` role now holds every `*.view` permission (previously it held zero permissions at all — see the Phase 1B RBAC redesign, `DATA_MODEL_DESIGN.md` §3.16). But `PermissionsGuard`'s existing logic (`if (!requiredPermission) return true`) still means any endpoint *not* behind an explicit `@RequirePermission(...)` check is accessible to any authenticated admin regardless of role, `Viewer` included. A well-designed permission set is not, by itself, sufficient if the underlying endpoints aren't correctly annotated with the right granular permission — an application-code concern (Phase 6) this schema change can't fix on its own.

## K. Constraint/index precision (5)

86. `Placement.packageLpa: Decimal(6,2)` (planned for the eventual cutover, not yet added to the live column in Phase 1) allows values up to 9999.99 — comfortably covers any realistic LPA figure, but would silently reject anything ≥ ₹10,000 LPA, worth stating explicitly rather than leaving implicit.
87. `DegreeVerification.cgpaOrPercentage: Decimal(5,2)` (added in Phase 1) allows up to 999.99 — covers both a 0-10 CGPA scale and a 0-100 percentage scale in the same column, but doesn't itself constrain a CGPA to ≤10 or a percentage to ≤100. A `CHECK` constraint was considered but not added, pending resolution of B.23's scale ambiguity.
88. Every `sortOrder Int @default(0)` field starts every pre-existing row at an identical `0` — providing no meaningful ordering until an admin manually re-orders. A naive `ORDER BY sortOrder` on unbackfilled data is an unstable sort unless a secondary tiebreaker (`id`/`createdAt`) is always included alongside it.
89. Most of the 55 new indexes are plain (non-unique) `@@index([...])`, existing purely for query performance and enforcing no constraint at all — easy to visually mistake "indexed" for "constrained." The design doc (§5) is explicit about which indexes are which for exactly this reason.
90. Composite indexes are ordered deliberately for their expected leading-query-column (`@@index([departmentId, type])` on `LearningOutcome`; `@@index([module, createdAt])` on `AuditLog`) — efficient for "all X for department Y" or "recent activity in module Z," but *not* efficient for the reverse-leading query pattern (e.g. "all PEOs across every department") without a separate index built for that access pattern.

## L. Timestamp / date semantics (4)

91. `Placement`/`Research`/`DegreeVerification`/`ExamNotification` all gained a brand-new `updatedAt @default(now()) @updatedAt` in Phase 1 — every *existing* row's `updatedAt` backfills to "the moment this migration ran," not its actual last-modified time (which was never recorded and can't be reconstructed). Any "recently changed" report must account for this migration-time cluster.
92. `Notification.startsAt`/`endsAt` have no `CHECK` constraint preventing `endsAt` from being set before `startsAt` — a logically invalid "ends before it starts" ticker notice is not rejected by the database; validate this at the application/DTO layer.
93. `Download.publishedAt @default(now())` fires on any row created without an explicit value — a future bulk-import script that forgets to set a real historical publish date will silently backdate every imported document to "whenever the import ran."
94. `deletedAt: null` is the *only* signal of "not deleted" (no separate `isDeleted` boolean for redundancy). In TypeScript, Prisma returns `null` (not `undefined`) for an unset nullable field — a `typeof x !== 'undefined'` check would be silently wrong here; only `!== null`/truthy checks are correct. An easy, quiet bug to introduce.

## M. Cross-entity data quality (7)

95. Nothing prevents `Faculty.departmentId` pointing at a `Department` that is `isActive: false` (or, once soft-delete is live, soft-deleted) — an inactive/deleted department can keep accumulating new faculty assignments unless the application layer blocks it at write-time. The FK only checks existence, not current status.
96. Similarly, nothing prevents linking `CommitteeMember.facultyId` to a Faculty row that is itself inactive or soft-deleted — a departed faculty member could be (re-)added to a committee roster with no schema-level objection.
97. `Admin.departmentId` and the department-scoped roles (`Department Administrator`/`Department Editor`) are *designed* to work together, but the schema permits an admin to hold a department-scoped role with `departmentId: null` (institution-wide), or an institution-wide role (`Faculty Manager`) while having a `departmentId` set. Neither combination is prevented; whether they're meaningful, harmless, or should be blocked is a Phase 6 product decision.
98. `News.authorAdminId` records who originally authored a piece, but there's no `updatedByAdminId` tracking who last *edited* it (distinct from who wrote it) — likely fine for a single-author CMS, but worth confirming, since `SiteSetting.updatedBy` gets exactly this tracking and `News` doesn't.
99. Nothing limits how many `Role`s a single `Admin` can hold via `AdminRole` — an admin could hold all 9 simultaneously. Whether the application's permission-checking logic correctly *unions* permissions across multiple held roles (rather than only checking the first one found) is a Phase 6 implementation-correctness concern this schema doesn't itself guarantee.
100. `Category.isActive` lets an admin hide a category from being newly assigned via the UI without deleting it (preserving referential integrity for existing content still pointing at it) — but nothing stops a direct API call from still assigning a new row to an `isActive: false` category, bypassing whatever UI-level filtering hides it from a dropdown. Enforcing "can't assign to an inactive category" at write-time, if desired, is an application-layer concern.
101. This entire review is schema-only by design — it deliberately does not attempt to re-catalog application-layer edge cases (race conditions in specific service methods, validation-pipe gaps, guard-ordering bugs) already covered by the earlier stabilization-phase audit. Read the two documents together for a complete picture of correctness risk across this codebase.

## N. RBAC granularity redesign (Phase 1B) (10)

102. The permission catalog grew from 13 rows to 63 between Phase 1 and Phase 1B — any existing `RolePermission`/`AdminRole` data seeded against the old 13-key catalog would need remapping onto the new keys. Since neither migration has ever been applied to a real database, this is a non-issue here, but it's exactly the kind of change that would need a careful data migration (not just a reseed) if Phase 1 had already gone live before Phase 1B was designed.
103. `degree_verification` permanently lacks a `.delete` permission anywhere in the catalog — not just "no role is granted it," but the key `degree_verification.delete` doesn't exist at all. A legitimate future need to delete a verification record (e.g. a confirmed duplicate/fraudulent entry) would require adding a new permission key first — an additive, non-breaking change, but a deliberate extra step, not a simple grant.
104. The seed script's `permissionsFor(...)` helper matches by `key.startsWith(\`${module}.\`)` — a textual prefix match. The trailing dot already guards against a hypothetical future module name being a prefix of another (e.g. `news` vs. `news_archive`), but this is a sharp edge worth remembering if the matching logic is ever copied elsewhere without the trailing dot.
105. `CONTENT_MODULES` (used to compute `CMS Administrator`'s permission set) is derived by excluding `admins`/`roles` from *every* module key programmatically — any future module added to `MODULE_ACTIONS` automatically flows into `CMS Administrator`'s grant with no one needing to remember to update that role by hand. Convenient, but it also means the role silently gains access to anything new without a dedicated review step for that specific role — worth a deliberate check whenever a module is added, not just trusting the automation blindly.
106. Same double-edged convenience for `Viewer`: `viewOnlyPermissions()` is computed from *every* permission ending in `.view`, including any added later — `Viewer` automatically gains view access to any new module with no code change to the `Viewer` role definition itself.
107. Every `Permission.description` is auto-generated from a template (`"${Verb} ${label}"`) rather than hand-written per permission — consistent and low-maintenance, but a hand-written description could be more specific than a mechanically generated one for permissions where "view/create/update/delete X" doesn't fully capture a nuance worth calling out.
108. Nothing in the schema enforces the `module.action` naming convention itself — `Permission.key` is a plain unique `String`, so a typo'd `faculty_view` (underscore instead of dot) would be silently accepted as a totally distinct, valid-looking permission key. The convention is enforced by discipline/code review, not the database.
109. `roles.update` (part of RBAC self-management) governs editing any role's permission set, but nothing schema-level distinguishes "can edit a role's ordinary permissions" from "can grant that role `admins.*`/`roles.*` themselves" — an admin holding `roles.update` could, in principle, grant a role they can edit the same privilege-escalation-capable permissions Super Admin holds, without ever directly holding `admins.manage`-equivalent power themselves. Confirm whether Phase 6 needs an explicit extra guard here (e.g. "only Super Admin can assign `admins.*`/`roles.*` to any role") beyond relying on seed-time convention.
110. `AdminRole.assignedAt` records *when* a role was assigned but not *by whom* — unlike almost every other mutable entity in this schema, there's no `assignedBy` column. Given role assignment is one of the most sensitive actions the system supports (per §14's audit-logging mandate), `AuditLog` can separately capture "admin X assigned role Y to admin Z" as an event without needing a dedicated column here — but only if Phase 6 actually wires that specific logging call in; nothing about `AdminRole`'s own shape guarantees it happens.
111. "Assigning roles to a user" isn't its own permission — it's folded into `admins.update`. This means anyone who can update an admin's basic profile (name, email) can also change what roles they hold, with no way to grant one capability without the other in the current catalog. Splitting this later (e.g. a dedicated `admins.assign_roles`) is an additive, non-breaking schema change if that distinction turns out to matter.

## O. Page-driven content entities (Phase 1B) (11)

112. `PageBanner.pageKey`, `ContentCard.section`, and `Faq.pageKey` all use the same "free-text, convention-based key matching a frontend route" pattern as `Department.slug`, but none are cross-validated against each other or against the frontend's actual route list. A typo'd `pageKey` (`"abuot"` instead of `"about"`) silently creates a banner no page will ever find, with no schema-level way to detect the mistake — the inherent cost of not hardcoding a page-route enum, which would itself need a migration every time a route is added.
113. `PageBanner.breadcrumbs` is a `Json` column with no schema-enforced shape — nothing stops storing a malformed value (a plain string instead of an array of `{label, href}` objects) that would only fail at render time in the frontend, not at write time in the API. Validate this shape explicitly in the DTO layer in Phase 6; Prisma's `Json` type provides zero structural validation on its own.
114. `SiteStatistic.scope`, `ContentCard.section`, and `PageBanner.pageKey` are three *different* free-text grouping conventions across three different tables, each invented independently in this phase — the same logical page (e.g. "homepage") is referenced by the literal string `"homepage"` in up to three unrelated tables with no referential integrity tying them together. A future shared `Page` lookup table (analogous to how `Category` unified the News/Gallery/Download taxonomies in Phase 1) is a plausible follow-up if this proliferation becomes unwieldy — not built now, to avoid pre-solving a problem that may not materialize.
115. `SiteStatistic.value: Int` can't represent a genuinely non-numeric "statistic" (e.g. a qualitative claim presented as a callout). Every stat the audit found was numeric-with-optional-suffix, but a future purely-textual stat-like callout won't fit this shape without either a schema change or misusing `suffix` to carry non-numeric meaning.
116. `ContactChannel.phones`/`emails` are `String[]` with no per-entry structure — no way to mark one number "primary" vs. "alternate," or distinguish a landline from a mobile. Any "first in the array is primary" convention is an application-layer choice, not schema-enforced.
117. None of the 10 Phase 1B entities carry a `departmentId` or any other scoping FK — all are assumed institution-wide based on the audit's findings. Confirm this before migrating real content into them; a department-specific variant of any of these patterns on a page the audit sampled too shallowly would need an additive column added before that content could be represented.
118. `ContentCard`'s generic design (§13, §3.29 of the design doc) means the database cannot enforce "a `homepage.services` card must have both a `title` and an `icon`" the way a dedicated table with non-nullable columns could — every field is nullable specifically because different `section` values need different subsets of them. Per-section required-field validation is entirely an application-layer/DTO responsibility keyed off `section`, not something the schema itself guarantees.
119. Because `ContentCard` rows for completely unrelated sections (`"homepage.services"` vs. `"iic.objectives"`) live in the same table, `@@index([section])` is what makes per-section queries efficient — but nothing at the schema level prevents a query that forgets its `WHERE section = ?` filter from mixing cards from every page together. Structurally analogous to the soft-delete "forgot the filter" risk already noted for the original Phase 1 entities (F.52).
120. All 10 Phase 1B entities were given soft-delete + optimistic-locking columns as a judgment-call extension of the originally-approved scope ("content," broadly), since none of them existed when that scope list was written — flagged explicitly for your review in §13's closing note, not something you'd already signed off on for these specific tables. If any of them (`ContentCard` is the most generic/lowest-stakes candidate) should be hard-deleted instead, that's a one-line schema change, not yet made.
121. `LeadershipProfile.slug` and `Department.slug` are independent unique-key spaces on two different tables — Postgres uniqueness constraints are per-table, so nothing prevents both from coincidentally choosing the same slug value (e.g. both slugged `"principal"`). Unlikely given how differently these two content types are typically named, but worth noting since both plausibly end up in similarly-shaped frontend URL paths.
122. Like the original Phase 1 review, this Phase 1B addition is schema-only — it doesn't examine whether the *frontend* will actually be migrated to consume these new tables (entirely unscoped, Phase 6 work), and it doesn't guarantee the underlying page-by-page audit was itself 100% exhaustive. A single research pass across a large, organically-grown frontend, however thorough, is not a formal guarantee every hardcoded content pattern was found — a second, more targeted pass before declaring full CMS coverage would be a reasonable follow-up.
