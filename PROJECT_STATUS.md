## 1. What this project is

A full-stack CMS-driven college website.

- **Backend:** NestJS + Prisma + PostgreSQL (`backend/`), JWT auth, permission-based RBAC, audit logging on every mutation.
- **Frontend:** Next.js App Router, fully static export (`output: "export"`, deployed to Netlify — no serverless functions). Public pages are static HTML with client-side data fetching layered on top for CMS-driven content. Admin panel is a client-rendered SPA behind login, served from the same static build.
- **Maturity:** started as a static site with hardcoded content; is now an enterprise-grade CMS with centralized media management, granular RBAC, full audit trails, and database-driven content across Homepage and Departments. Remaining work is business workflows (Careers), refinement, and production hardening — not core infrastructure.

### Careers Application Pipeline (Roadmap Phase 1 — complete)

Full recruitment workflow: Apply Now → Form → Resume Upload → Confirmation Email → HR Email → Stored in CMS.

- **`NotificationService`** (`backend/src/mailer/`) — the provider-agnostic email abstraction the user required. Application code depends only on `NotificationService.send()`; concrete providers (`ConsoleEmailProvider`, `SmtpEmailProvider`, `SesEmailProvider`) are selected purely by the `EMAIL_PROVIDER` env var (`console` default / `smtp` for Gmail SMTP or Mailpit / `ses` for AWS SES via `@aws-sdk/client-sesv2`, using nodemailer's native SES transport). A failed send is logged, never thrown — an email outage can't fail an application that's already saved.
- **`CareerApplication`** model (+ `CareerApplicationStatusHistory` for the timeline, + `ApplicationStatus`/`ApplicationSource` enums). Deliberately no soft-delete/version — a compliance-adjacent HR record corrected by status transition, never deleted.
- **Resumes are Media Library `DOCUMENT` assets**, per the user's explicit suggestion — reuses the full upload/validation/dedup/storage pipeline. Added `.doc` support to the Media Library's allowed types (previously only pdf/docx/xlsx/pptx). Resumes are **not** served through the Media Library's public unauthenticated file route (PII) — a dedicated permission-gated `GET /career-applications/admin/:id/resume` streams them instead.
- **Public submission is unauthenticated** by necessity; a seeded "System (Public Submissions)" service-account `Admin` row (`isActive: false`, unusable password, can never log in) provides the Media/AuditLog attribution every other upload path requires a real admin for.
- **Duplicate-submission prevention**: same email + same job posting within a configurable window (`CAREER_APPLICATION_DUPLICATE_WINDOW_HOURS`, default 24h) → `409 Conflict`.
- **Admin UI**: `/admin/careers/applications` — search/filter/pagination, status timeline, notes, assign HR, resume download, CSV + Excel export (`exceljs`). Dashboard gained a "Job Applications" widget (5 tiles: Today/This Week/Pending Review/Shortlisted/Selected) plus a standard total-count tile in the main overview grid.
- **Bug found and fixed as a side effect**: the admin layout's flex content column had no `min-w-0`, so any sufficiently wide table (this one has 7 columns) blew out the whole page into horizontal scroll on mobile instead of scrolling internally. Fixed in `app/admin/layout.tsx` — benefits every admin table page, not just this one.
- 358/358 backend tests passing (11 new). Full live E2E verified via Playwright: submission, resume upload, HR + confirmation emails (console provider), duplicate-block, admin list/status/notes/assign-HR/export/resume-download, audit log trail, mobile responsive on both the public form and admin list.
- **Not yet done**: real SMTP/SES send was not live-tested (no Gmail/Mailpit/AWS credentials available in this environment) — only unit-tested and verified via the console provider. Verify with real credentials before relying on it in production.

### Centralized Announcement & Ticker Engine (Roadmap Phase 2 — complete)

One engine replaces what would otherwise have been N separate ticker mechanisms across News/Events/Exam Notifications/Placements/Admissions/manual notices.

- **`Announcement`** model (title, body, `AnnouncementPriority` CRITICAL/HIGH/NORMAL/LOW, `AnnouncementSource`, optional `link`/`openInNewTab`, `startDate`/`endDate` for auto-expiry, `isPublished`/`isActive`, `sortOrder`, soft-delete/restore/version) + **`AnnouncementPlacement`** join table (`{announcementId, location, departmentId?}`, unique per combination). "Reusable across multiple locations" is literally the presence/absence of placement rows — the same one-row-per-toggle philosophy as `DepartmentDisplaySetting`, not boolean columns per location.
- **`AnnouncementLocation`** enum covers all 6 required placements: Header Ticker, Hero Banner, Homepage Section, Department Page (optionally department-scoped via `departmentId`), Admissions Page, Placements Page.
- **Priority ordering is free**: `AnnouncementPriority` is declared `CRITICAL, HIGH, NORMAL, LOW` in that exact order, and PostgreSQL native enums compare by declaration order — `ORDER BY priority ASC` sorts critical-first with no extra numeric column or `CASE` expression. Verified live with a 3-item test batch.
- **Auto-expiry is query-time filtering**, not a cron job — `findAllPublic()` excludes rows outside `[startDate, endDate]` on every read. Verified live (a 2020-dated `endDate` item was correctly excluded).
- **`AnnouncementTicker.tsx`** — one reusable component for all 6 display locations (CSS marquee via duplicated-content + `translateX(-50%)`, `animation-play-state: paused` on hover, priority-based background coloring, `compact` prop for header-strip sizing, click-through link support). Wired into: `ChromeGate.tsx` (HEADER_TICKER, in the previously-empty gap between Header and Navbar), `Hero.tsx` (HERO_BANNER), `app/page.tsx` (HOMEPAGE_SECTION), `DepartmentPage.tsx` (DEPARTMENT_PAGE, department-scoped), `app/admissions/page.tsx` (ADMISSIONS_PAGE), `app/placements/overview/page.tsx` (PLACEMENTS_PAGE).
- **Admin UI**: `/admin/announcements` (new first entry in the sidebar nav) — full CRUD, a location checkbox grid for multi-placement assignment, conditional department picker (only shown when Department Page is checked), publish/unpublish toggle, soft-delete/restore.
- **Deliberate scope boundary**: `Hero.tsx` already had a separate, pre-existing `newsTicker` field/mechanism (its own admin editor, vertical-scroll ticker). The new centralized `AnnouncementTicker` (HERO_BANNER) was added **alongside** it rather than migrating/removing it in this pass — a full migration (deleting the admin field, migrating existing data) was judged too risky to attempt untested within an already-large single pass. Flagged as explicit follow-up, not forgotten. See Tech Debt (§8).
- **Not built this pass** (explicitly out of the user's literal spec, using existing `source`/`sourceModule`/`sourceRecordId` fields as the hook for later): a "Promote to Announcement" convenience action from News/Events/Exam Notifications admin list rows.
- 368/368 backend tests passing (10 new). Live-verified: creation with multi-location placements, priority ordering, auto-expiry, department-scoped placement filtering (dept 5 shows its announcement, dept 6 correctly doesn't), publish/unpublish gating, and visual confirmation via screenshot of the header ticker rendering correctly in the Header/Navbar gap.

## 3. The scalable Display Settings pattern

`DepartmentDisplaySetting`: one row per `(departmentId, key)`, `value: Boolean @default(true)`. Absence of a row = visible. A code-defined catalog (`DEPARTMENT_DISPLAY_SETTINGS_CATALOG`, 22 keys) drives both the admin toggle grid and the public page's gating — adding a new toggle is a one-line catalog addition, never a migration. Currently section-level only (e.g. `faculty.showSection`); field-level granularity (`faculty.showPhotos`, `hod.showMessage`, etc.) exists in the catalog but isn't wired into the public page's rendering yet — see Roadmap / Tech Debt.

The homepage has a separate, older, simpler mechanism (`SectionVisibilityService`, one flag per homepage section) — not unified with the Department Display Settings engine. Worth consolidating eventually, not urgent.

**Phase 3 — Homepage cache/update investigation — ✅ complete.**
Root cause found and fixed: `media-file.controller.ts` served every Media Library file (images, videos — including Hero backgrounds and homepage banners) with `Cache-Control: public, max-age=31536000, immutable`. The URL scheme (`/media/file/:mediaId/:variant/:format`) is deliberately stable across a "Replace" operation (old `MediaVariant` rows are deleted and recreated with new storage keys, same URL) — but `immutable` told every browser to never re-request that URL for a year, so replacing a homepage image/video via the Media Library was invisible to anyone who'd already loaded the old one. Fixed by adding an `ETag` (`"media-<variantRow.id>"`, which changes on every Replace since old rows are deleted/recreated, not updated in place) and changing `Cache-Control` to `public, max-age=300, must-revalidate` — repeat loads within 5 minutes stay cheap, but any Replace is visible on the very next request via a 304-validated revalidation instead of only after a year. Verified live: fresh request returns the new `ETag`/`Cache-Control`; a conditional request with `If-None-Match` matching the current variant correctly returns `304`.
Ruled out (checked, not the cause): no client-side data caching layer (SWR/localStorage/service worker — all homepage sections are `"use client"` components that `fetch` fresh on every mount), no backend in-memory cache module, no global `Cache-Control` on JSON API responses, section-visibility (`VisibilityWrapped<T>`) is resolved server-side per-request, not baked into the static export at build time. Also audited every homepage-module service's public query method (`Hero`, `Statistics`, `QuickLinks`/`AdmissionPrograms`/`Departments` via `ContentCardService`, `Sections`, `Testimonials`, `CampusVideos`, `AccreditationBadges`, `Recruiters`) — all correctly filter `{isActive: true, deletedAt: null}` (or `status: PUBLISHED` for Sections), so soft-deleted/unpublished content cannot leak through at the query level.

**Live end-to-end verification** (real HTTP calls against a running backend, not just code audit): Testimonials create → visible on the public endpoint on the very next request, no delay; soft-delete → gone on the very next request; restore → back on the very next request. Section (Vision) unpublish (`status: DRAFT`) → public endpoint immediately returns `null`; republish → immediately returns data again. Media file `ETag`/`Cache-Control` fix verified live (200 with fresh `ETag` on first request, 304 on a matching conditional re-request). Every mutation's effect was visible on the *first* subsequent GET with no special cache-busting headers sent — matching what a real browser reload does, since there is no server-side or client-side caching layer sitting between a page load and the live API. **Real-browser (Playwright) delete-immediacy check**: created a testimonial, confirmed it renders in an actual browser tab, deleted it via the API (simulating an admin acting in another tab), then did a plain `page.reload()` in the *same* tab — the item was gone, ruling out the browser's own HTTP cache (which curl, used for the rest of this investigation, never exercises) as a source of "deleted content still appears."

**Follow-up deep audit, per an explicit user request to check every asset type by name** (Homepage Hero image/video, Gallery image/video, Faculty photo, Department hero image, Recruiter logo, Testimonial image, Accreditation logo, Site logo, Favicon) for Replace + Version History correctness:

- **Found and fixed a second, more serious bug** (data loss, not caching): `MediaService.replace()` deleted the old file's `MediaVariant` rows *before* the DB row update that points at the new file. If that update failed for any reason - reproduced live via a checksum collision (re-uploading content whose SHA-256 already exists under a different `mediaId`, which raised a raw, unhandled Prisma unique-constraint error) - the old variants were already gone, the update never committed, and the asset was left permanently 404ing with no way to recover the deleted variants. Two real media assets were broken this way during live testing and had to be repaired by re-uploading their still-intact original files (their `ORIGINAL/SOURCE` file itself survives a partial replace, since `deleteVariantsForMedia` protects it from physical deletion - only its DB row was lost). Fixed by: (1) checking for a checksum collision against a *different* row up front and rejecting with a clear `409 ConflictException` before touching anything, (2) reordering so the DB update commits *before* the old variants are deleted, (3) deleting the newly-saved (now orphaned) file if the update still fails for some other reason. `media.service.spec.ts` had zero test coverage for `replace()` before this - added 4 regression tests (collision rejection, self-checksum no-op, update-before-delete ordering, cleanup-on-failure). 372/372 backend tests passing.
- **Accreditation Badge had no Media Library integration at all** - `imageUrl` was a plain string with no `mediaId` column, unlike every sibling module (Recruiters, Testimonials, Faculty, Hero, Gallery, Department). Fixed to match the established pattern exactly: added `mediaId Int?` (migration `20260712010000_accreditation_badge_media`), wired `MediaLinkService.prepareLink()`/`syncUsage()`/`untrackAll()` into create/update/delete/restore, and replaced the admin form's plain URL text field with `MediaField`. Accreditation logos now support Replace/Version History like every other image type.
- **Per-type findings, reported honestly rather than assumed**: of the 11 named types, 7 are genuinely Media-Library-backed and now behave correctly (Homepage Hero video, Gallery image, Faculty photo, Department hero image via `heroMediaId`, Recruiter logo, Testimonial image, Accreditation logo). ## 8. Known technical debt

- **Faculty department linkage is dual**: real `departmentId` FK *and* legacy `department` free-text string, kept in sync on every save. The free-text string still drives the public site's `GET /faculty?department=` and `GET /faculty/hod/:department` lookups. Not urgent to unify, but a real inconsistency to be aware of.
- **Research module is intentionally minimal**: no soft-delete, no version/optimistic-locking, no reorder — inconsistent with every other content module's shape. Was a deliberate scope decision, not an oversight, but worth flagging if Research ever needs the same protections as everything else.
- ~~Display Settings catalog has unused entries~~ — ✅ fixed in Phase 5 (see §7): every field-level catalog key is now read and gated by `DepartmentPage.tsx`.
- **Two separate section-visibility mechanisms**: `SectionVisibilityService` (homepage only, older) and `DepartmentDisplaySetting` (departments, newer/more scalable). Not unified.
- **`reorder` endpoints are not department-ownership-scoped** (Labs, Gallery, Downloads, Department Programmes, Learning Outcomes, Department Highlights, Contact Channels) — a department-scoped admin could technically reorder another department's items, though not view/create/edit/delete their content. Lower-risk than the create/update/delete gaps that were fixed (reordering doesn't change ownership or content, just display order), and the reorder DTOs' batch shape (`{id, sortOrder}[]`) doesn't carry one clean target department to check against without an extra per-item DB lookup per request. Worth closing in a future pass.
- **Legacy `Admin.department` free-text field and the new `Admin.departmentId` FK now coexist** in the Admins UI (`AdminsManager.tsx` shows both: "Department (optional, legacy label)" and "Department ownership (RBAC scope)") — the legacy field is display-only text with no enforcement behavior; only `departmentId` is read by `DepartmentOwnershipGuard`. Not unified/removed since the legacy field may still be referenced elsewhere; low-risk to leave as-is.
- **Media Library storage is local-disk only.** `StorageAdapter` interface exists for an S3/CloudFront swap, but no cloud adapter is implemented. No virus scanning (no ClamAV in this environment). No video transcoding (originals only, one variant).
- **Department hero banners are emblem/logo graphics**, not photographic banners — visually acceptable per user sign-off, not ideal long-term.
- **Hero has two independent ticker mechanisms**: the pre-existing `HomepageHero.newsTicker` field (its own admin editor, vertical-scroll) and the new centralized `AnnouncementTicker` (HERO_BANNER location) render side by side rather than being unified. A full migration (remove the old field, migrate any existing data, update the Hero admin editor) was deliberately deferred rather than risked within the Announcement Engine's single delivery pass. Worth consolidating in a future pass — not urgent, not a functional bug.
- **No "Promote to Announcement" convenience action** from News/Events/Exam Notifications admin list rows — the `Announcement` model's `source`/`sourceModule`/`sourceRecordId` fields exist to support this later; announcements must currently be created manually even when they mirror an existing News/Event item.
- **Site logo and favicon are static build-time files with zero CMS wiring** (`frontend/public/header.png` via `next/image` in `Header.tsx`; `frontend/app/favicon.ico`, the Next.js convention file) — neither is a `SiteSetting`/Media Library asset today, so updating either requires a code change and redeploy, not an admin action. `SiteSetting` already has the generic `mediaId`/`type: IMAGE_URL` mechanism to support this; wiring it up is a reasonable follow-up but touches root-layout behavior (the favicon especially, since it's a build-time convention file, not a normal `<img>`) enough to deserve its own scoped pass. Found during the Homepage Reliability asset-type audit, not fixed in that pass.
- **A Replace whose async variant-processing fails afterward leaves the asset with zero variants and no fallback** (`processingStatus: FAILED`, permanent 404) — the old variants are correctly deleted only *after* the new DB row commits (see §7 Phase 3's Replace fix), but nothing currently keeps them alive until the *new* variants actually finish generating successfully. Real admin uploads are unlikely to hit this in practice (extension/MIME/magic-byte validation catches the common bad-file cases before this point), but a genuinely corrupt-past-validation file can still cause it. A proper fix would need the processing queue to do a "keep old, swap only on success" handoff rather than delete-then-regenerate. Not fixed - narrower and riskier to change than the collision/ordering bug that was fixed, so flagged for a dedicated pass instead.

## 9. Production blockers (before real deployment)

- **No backend hosting/deployment config** — Netlify serves the frontend static export only; the NestJS backend needs a home (Docker + a host, or similar) that doesn't exist yet. Now Roadmap Phase 6.
- **Email provider abstraction exists but is untested against a real provider** — `NotificationService`/`SmtpEmailProvider`/`SesEmailProvider` are built and unit-tested, but no Gmail App Password, Mailpit instance, or AWS SES credentials were available in this environment to verify a real send.
